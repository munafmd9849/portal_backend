Executive summary

This portal is a strong campus placement MVP (~66% average vs real TPO / industry standards) — not production-grade for a live drive with 500+ students without fixes. Strongest: assessments + proctoring, guided AI mocks, resume builder, application tracker, job moderation model, interview round evaluations. Weakest: offer/join closure, notifications UX (disabled for students), placement policy engine, scoped admin data leaks, broken no-screening interview path, audit coverage, centralized placement calendar.

Student — where standards are not met

Notifications UI disabled — Notification.jsx loads data then return null. Real apps: bell, unread count, Socket.IO push. Fix: restore UI; wire to existing backend.
Profile completion gate is frontend-only — incomplete profile blocked in UI but getTargetedJobs still returns jobs. Fix: API returns empty or 403 until profile complete.
OTP optional on registration — email verification not enforced unless token sent. Fix: require verified email before apply.
Resources = AI chatbot — not institutional prep materials, policies, formats. Fix: CMS for PDFs, videos, company prep packs.
StudentDashboard.jsx ~5,100 lines — real teams split by route/feature for testability. Fix: extract tabs to lazy routes.

Key files: StudentDashboard.jsx, StudentApplicationTracker.jsx, Notification.jsx, JobApplyQuestionsModal.jsx, StudentAssessments.jsx, GuidedAiInterviewsStudent.jsx

Admin / Super Admin — where standards are not met

Student Directory API ignores admin scope — scoped campus admins may see all students via /api/admin/student-directory. Real TPO: strict data isolation. Fix: apply getAdminScopeFilter in adminStudentDirectory.js.
Job moderation hidden from sidebar — jobPostingsManager tab commented out; IN_REVIEW jobs can pile up unnoticed. Fix: dashboard queue + sidebar link.
Super Admin vs Admin tab mismatch — Super Admin lacks assessments, mock interviews, announcements that regular Admin has. Fix: unified role matrix.
No placement policy engine — dream company tiers, max offers, dual placement, min mocks before live drive. Fix: policy rules engine blocking apply/select.
Endorsements: no admin module — student-initiated only; no fraud review or eligibility gate. Fix: admin queue + min endorsement policy.
Audit logs sparse — most admin actions (assessments, screening, mocks) not logged. Fix: logAction on all mutating controllers.

Key files: AdminDashboard.jsx, StudentDirectory.jsx, JobPostingsManager.jsx, CreateDisableAdmins.jsx, adminScope.js, AuditLogs.jsx

Recruiter — where standards are not met

Screening is token-page only — no persistent logged-in screening workspace in main dashboard. Real recruiters expect ATS-style applicant list.
Weak company onboarding — MOU PDF upload exists; missing GST verification, agreement expiry, multi-POC hierarchy.
No offer rollout tools — recruiter cannot issue offer letters or track acceptance in portal.

Key files: RecruiterDashboard.jsx, RecruiterScreening.jsx, recruiters.js, RecruiterApplicantHistory.jsx

Platform & infrastructure — where standards are not met

No backend .env.example — frontend has one; backend onboarding incomplete for deploy.
Proctoring trust model — client-side tab/face checks; determined cheaters bypass. Real high-stakes OA needs server-side proctor review + identity.
Google OAuth tokens in URL query — security smell; use postMessage or httpOnly cookies.
Legacy duplicate app — AI_Interview_Resume-main/ folder is separate mini-app, not integrated.
Render Postgres pool exhaustion — schedulers hammer DB; use pgBouncer, connection_limit, backoff on P2024.

Key files: server.js, auth.js, database.js, ProctoringEngine.js, googleLogin.js

P0 — Blockers (fix first)

Critical Issue #1

No pre-interview path broken on Interview Scheduling

Problem: When both requiresScreening and requiresTest are false, Create Job says all applicants become interview-eligible after deadline. Reality: applicants stay APPLIED. interviewScheduling.js only loads INTERVIEW_ELIGIBLE / TEST_SELECTED → 0 candidates, Round 1 empty. Legacy interviews.js handles this correctly; the admin UI uses Interview Scheduling.

Solution (10/10)

  • Central helper: getInterviewEligibleApplications(job) — if !screening & !test → all non-rejected APPLIED; else → INTERVIEW_ELIGIBLE only.
  • Use helper everywhere: session candidate count, Round 1 list, end round, incomplete session updates.
  • Option A: include APPLIED in queries when no gate. Option B: auto-promote to INTERVIEW_ELIGIBLE after deadline (cron or on session open).
  • Align student tracker: show Resume/QA as “Not required”, not Pending.
Critical Issue #2

Two parallel interview systems

Problem: Legacy Interview + InterviewEvaluation coexist with InterviewSession + InterviewRound + RoundEvaluation. Same product, duplicate logic; bugs fixed in one path only. Confuses devs and admins.

Solution (10/10)

  • Pick InterviewSession as single source of truth (already used by admin UI).
  • Deprecate legacy routes; migrate any remaining UI off /api/admin/interview/:id token flow or bridge both to one model.
  • One eligibility helper, one evaluation schema, one student timeline builder fed from session data.
Critical Issue #3

Custom apply questions are display-only

Problem: Admin adds custom questions on job create; student sees modal before apply, but answers are not persisted on the application. Real drives use these for audit, shortlisting, and recruiter review.

Solution (10/10)

  • Add Application.customAnswers JSON (question → answer) or ApplicationQuestionAnswer table.
  • POST apply payload includes answers; validate required questions server-side.
  • Show answers in admin applicant detail, recruiter screening, and export spreadsheet.
  • Separate from requiresTest (recruiter QA gate) — custom Q = apply-time data collection.
Critical Issue #14

Student Directory bypasses scoped admin access

Problem: getAdminScopeFilter is used on jobs/applications but not on /api/admin/student-directory. A campus-scoped admin may see students outside their school/center/batch — real-world compliance failure.

Solution (10/10)

  • Merge scope filter into all student directory queries and panel APIs.
  • Integration test: scoped admin cannot fetch out-of-scope student IDs.
Critical Issue #15

Student notifications UI disabled

Problem: Backend + Socket.IO work; Notification.jsx returns null — students get no in-app alerts for drives, queries, results.

Solution (10/10)

  • Restore notification bell + modal; unread badge; real-time via existing socket events.
  • Critical drive events also via email/SMS (Indian campus standard).

P1 — High priority

Issue #4 — Student tracker misleads when screening not required

Shows “Under Review” / “Resume Screening Pending” even when flags are off.

Solution: In applicationTrackerState.js, skip pending resume/QA steps when !requiresScreening / !requiresTest. Primary status for no-gate jobs after apply: “Eligible for interview” (after deadline) or “Applied — awaiting drive”.

Issue #5 — Eligibility enforcement inconsistent

YOP check only when ENFORCE_YOP=true. CGPA/backlogs partially enforced. Real TPO always validates on server.

Solution: Single validateStudentEligibility(student, job) used by apply API always (CGPA, backlogs, YOP, gap, targeting). Frontend mirrors for UX; backend is authoritative. Remove env-gated YOP.

Issue #6 — requiresScreening !== false treats undefined as required

In applications.js, missing flag reads as screening required.

Solution: Use explicit Boolean(job.requiresScreening) everywhere. Default in schema is already false.

Issue #7 — QA/Test is manual screening, not real OA

“QA required” = recruiter marks pass/fail in screening UI, not linked Assessment Engine.

Solution (10/10): When requiresTest, attach optional assessmentId on job. Student must complete assessment; auto-set TEST_SELECTED / TEST_REJECTED from score cutoff. Keep manual override for edge cases.

Issue #8 — Post-interview stops at SELECTED

No OFFERED → ACCEPTED → JOINED, offer letter, CTC, document collection, acceptance deadline.

Solution: Extend application lifecycle: OFFERED, OFFER_ACCEPTED, OFFER_DECLINED, JOINED. Admin “Declare results” step after session COMPLETED. Student accept/decline portal. Notifications + audit log.

P2 — Medium priority

Issue #9 — Drive lifecycle states too coarse

Only broad job status (IN_REVIEW, POSTED, etc.). Ops need: Applications Open → Closed → Screening → Interviews Live → Results Declared.

Solution: Derived or explicit drivePhase from deadline, screening finalization, session status, results published flag.

Issue #10 — Dual approve vs post paths

approveJob and postJob overlap; comments say different approval rules.

Solution: One admin action: Review → Approve & Post (or Reject with reason). Super-admin vs scoped-admin permissions only difference.

Issue #11 — Fragmented candidate state fields

status, screeningStatus, interviewStatus, pipelineStatus can drift.

Solution: buildApplicationTrackerState as single read model; all writes go through transition functions with validation (state machine).

Issue #12 — Interview ops gaps

No per-candidate slots, room assignment, no-show tracking, reschedule workflow.

Solution: Optional Phase 2: interview slot booking, panel calendar sync (Google Calendar hook exists), attendance mark at round entry.

Issue #13 — analyzeCandidates import was commented out

Fixed once by uncommenting import; pattern shows fragile optional features.

Solution: Integration test per exported controller action; CI fails if symbol undefined.

P3 — Polish & ops

  • DB connection pool on Render free tier — use connection limit in DATABASE_URL, pgBouncer, or local dev DB; schedulers should backoff on P2024.
  • Results publication — lock edits after “Declare results”; bulk notify students selected/rejected.
  • Audit completeness — screening decisions, round evaluations, offer actions in audit log.
  • Export parity — spreadsheet includes custom answers, screening remarks, all round scores.
  • Removed features cleanup — Conversational AI removed; optional schema column cleanup migration later.

Target 10/10 — Definition of done

Every job configuration path works end-to-end without manual DB fixes.

  1. Placement drive: Any job config works E2E — apply → screen (if any) → interview → outcome.
  2. Student: Notifications live; profile gate on API; apply answers stored; eligibility always server-side.
  3. Admin: Scoped data isolation everywhere; moderation queue visible; centralized placement calendar.
  4. Policy: Dream/super-dream tiers, dual-placement rules, min mocks/assessments before apply (configurable).
  5. Offers: OFFERED → ACCEPTED/DECLINED → JOINED with CTC and documents.
  6. Audit: Every mutating action logged; results declaration locks edits.
  7. One truth: Student, admin, recruiter see same status from one tracker builder.
  8. Quality: Integration tests + backend .env.example + no god components.
